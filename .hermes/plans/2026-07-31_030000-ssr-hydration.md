# SSR Hydration Plan

**Problem:** `/loras` and `/loras/[id]` pages show a spinner on every visit while tRPC queries fire client-side, even though the data doesn't change often.

**Current pattern:** All data fetching happens client-side via tRPC queries (`useQuery`). The page renders a Loader until the API responds.

## Approach: `getServerSideProps` with direct DB queries

Server-render the initial data by querying MongoDB directly in `getServerSideProps`, then pass it as `initialData` to the existing tRPC queries. This eliminates the initial loader flash — the page hydrates with data already present.

We use the same `getDb()` function from `server/api/db.ts` so there's no duplication.

### Pages affected

| Page | Current | After SSR |
|------|---------|-----------|
| `/loras` | LoraGallery → `trpc.lora.list.useQuery()` | `getServerSideProps` fetches list, passes as initialData |
| `/loras/[id]` | `trpc.lora.getById.useQuery()` + `trpc.generate.listByLora.useQuery()` | `getServerSideProps` fetches lora data, passes as initialData |

### Implementation

#### 1. `/loras` page

Add `getServerSideProps`:
```typescript
export const getServerSideProps: GetServerSideProps = async () => {
  const db = await getDb();
  const docs = await db
    .collection<LoraTrainingDoc>("lora_trainings")
    .find({ status: "completed", hidden: { $ne: true } })
    .sort({ createdAt: -1 })
    .toArray();

  const loras = docs.map((doc) => ({ /* same shape as list return */ }));

  return { props: { initialLoras: loras } };
};
```

Then in `LoraGallery`, accept `initialLoras` as prop and pass it as `initialData`:
```typescript
const { data } = trpc.lora.list.useQuery(undefined, {
  initialData: initialLoras,
});
```

#### 2. `/loras/[id]` page

Same pattern — `getServerSideProps` fetches the single lora and generated images, passes them as `initialData` to the two queries.

### Why not tRPC's built-in SSR?

tRPC's SSR (`ssr: true` + `withTRPC` HOC) requires restructuring the entire tRPC client setup in `_app.tsx`, adding middleware, and reworking the provider pattern. The direct DB approach is simpler, equally effective for initial page load, and requires no architectural changes.

### Risks

- **Stale data**: `getServerSideProps` runs on every request so data is fresh. No staleness concern.
- **Code duplication**: The list transformation logic is duplicated between SSR and the tRPC procedure. Mitigated by extracting a shared helper function.
- **DB connection**: `getDb()` already handles connection pooling via a singleton — safe to call from SSR context.
